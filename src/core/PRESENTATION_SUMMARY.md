# AI-Powered Bitcoin Transaction Monitoring System

## Presentation Summary in Easy Words

## 1. Project Introduction

This project is an offline AI-powered system for monitoring and analyzing Bitcoin transaction traffic.

The system studies transaction information and network information to find wallets or entities that behave differently from normal users. It then gives each wallet a risk level, explains the reason for the risk, and creates ranked results for a dashboard.

The system is designed to work without Internet access. It does not depend on live blockchain APIs, cloud APIs, online AI services, or online dashboards during execution.

This is currently a development prototype based on synthetic data. Synthetic data means artificially generated data that looks like Bitcoin transaction data but does not represent real users.

## 5. Suspicious Patterns in the Dataset

### Fan-out

One wallet sends funds to many different wallets in a short time.

```text
Wallet A -> Wallet B
Wallet A -> Wallet C
Wallet A -> Wallet D
```

This may represent distribution or splitting of funds.

### Fan-in

Many wallets send funds to one wallet.

```text
Wallet A -> Wallet Z
Wallet B -> Wallet Z
Wallet C -> Wallet Z
```

This may represent collection or consolidation of funds.

### Rapid Transfer Chain

Funds move through a chain of wallets quickly.

```text
Wallet 1 -> Wallet 2 -> Wallet 3 -> Wallet 4
```

This may represent layering or an attempt to make fund tracing more difficult.

### High-Frequency Burst

One wallet or entity performs many transactions in a very short period.

For example, the synthetic dataset includes transactions occurring every few seconds for one burst entity.

## 6. Folder and File Explanation

### `requirements.txt`

This file lists the Python libraries required by the project.

Important libraries include:

- `pandas` for table and dataset processing
- `numpy` for numerical calculations
- `scikit-learn` for machine learning and evaluation
- `hdbscan` for behavioral clustering
- `networkx` for graph analysis
- `pyarrow` for Parquet files
- `matplotlib` for charts
- `lxml` for XML processing
- `joblib` for saving trained models
- `shap` is listed for explainability support, although the current implementation uses z-scores
- `pyyaml` is listed for configuration support

### `scripts/generate_dev_data.py`

Creates the synthetic development dataset with normal and suspicious transaction patterns.

It saves the data under the development data folder.

### `scripts/run_step2.py`

Runs correlation and graph construction.

It:

- Loads and validates the dataset
- Correlates wallets with IPs, ASNs, and countries
- Builds the NetworkX graph
- Prints graph statistics
- Tests multi-hop wallet connections
- Creates a degree-distribution chart

### `scripts/run_step3.py`

Runs feature engineering.

It:

- Loads the cleaned transaction data
- Builds the graph
- Creates wallet-level numerical features
- Checks that ground-truth columns are not included
- Saves the features as `features.parquet`
- Prints missing values, statistics, and correlations

### `backend/ingestion/ingestor.py`

Loads input files in CSV, JSON, or XML format.

It normalizes column names and sends the data to the validator.

### `backend/validation/validator.py`

Checks whether the transaction data is valid.

It checks:

- Required columns
- Missing transaction IDs
- Missing timestamps
- IP address format
- Port ranges
- Transaction ID format
- Empty address or amount lists
- Negative amounts and fees
- Duplicate transaction IDs
- Input/output amount consistency

It also fills missing optional values and creates a data-quality report.

### `backend/correlation/correlator.py`

Creates associations between:

- Wallets
- IP addresses
- Transactions
- ASNs
- Countries

It produces wallet-network and IP-transaction association tables.

### `backend/graph/graph_builder.py`

Builds a heterogeneous directed graph using NetworkX.

Node types include:

- Wallet
- Transaction
- IP address
- ASN
- Country

Edge types include:

- Wallet to transaction
- Transaction to wallet
- Wallet to IP
- IP to ASN
- IP to country

It also supports multi-hop investigation. For example, it can find wallets connected to another wallet within two or four hops.

### `backend/features/feature_engineering.py`

Creates numerical behavior features for every wallet.

It calculates transaction, wallet, time, graph, and network features.

### `backend/features/feature_extractor.py`

Provides a more advanced feature-extraction path. It creates wallet features and keeps ground-truth information separately for evaluation.

### `backend/ml/isolation_forest_model.py`

Uses Isolation Forest to detect unusual wallets without needing labels during training.

The model uses:

- 100 trees
- Contamination of 0.05
- Random state of 42

A lower or more negative anomaly score means the wallet is more unusual.

### `backend/ml/hdbscan_clustering.py`

Uses HDBSCAN to group wallets with similar behavior.

Before clustering, features are standardized using `StandardScaler` so that large-valued features do not dominate smaller-valued features.

Cluster label `-1` means that HDBSCAN considers the wallet noise or an outlier.

### `backend/ml/train_model.py`

Contains a separate supervised Random Forest experiment.

It:

- Loads 20,000 transaction rows
- Creates 11 numerical features
- Splits data into training and testing sets
- Uses 300 decision trees
- Handles class imbalance using balanced class weights
- Calculates precision, recall, F1, confusion matrix, and ROC-AUC
- Saves the model with Joblib

This Random Forest path is separate from the main Isolation Forest plus HDBSCAN pipeline.

### `backend/alerts/generate_alerts.py`

Combines anomaly results and clustering results.

It creates:

- HIGH risk
- MEDIUM risk
- LOW risk

Rules:

- HIGH: anomalous and HDBSCAN noise
- MEDIUM: anomalous or HDBSCAN noise
- LOW: neither anomalous nor noise

### `backend/risk/risk_score.py`

Creates a continuous risk score between 0 and 100.

Default calculation:

- Anomaly contribution: up to 80 points
- Cluster outlier contribution: up to 20 points

A wallet marked as HDBSCAN noise receives the cluster boost.

### `backend/explainability/explain_risk.py`

Explains why a wallet is unusual.

It uses z-scores to compare each wallet feature with the average feature value of all wallets.

The three features with the largest absolute z-scores are converted into readable text.

Example:

```text
High tx per hour (19.5x avg),
High in degree (2.7x avg),
Low avg amount (0.2x avg)
```

### `backend/evaluation/evaluate_model.py`

Compares the system's risk flags with the synthetic ground-truth labels.

It calculates:

- Precision
- Recall
- F1 score
- Confusion matrix
- Classification report

### `backend/output/finalize_output.py`

Creates final files for dashboard integration.

It:

- Selects the required columns
- Resets the wallet index into a normal column
- Rounds risk scores
- Sorts wallets by descending risk score
- Creates CSV output
- Creates formatted JSON output

### `outputs/final/`

Contains the final ranked results:

- `ranked_results.json`
- `ranked_results.csv`

### `outputs/alerts/`

Contains entities marked HIGH or MEDIUM risk.

### `outputs/evaluation/`

Contains the model evaluation report.

### `tests/`

Contains automated tests for ingestion, validation, graph analysis, feature engineering, ML, risk scoring, explainability, evaluation, and output formatting.

## 7. Feature Engineering in Simple Words

Raw transactions are difficult for an ML model to understand directly. Therefore, the system changes them into numerical wallet profiles.

### Transaction Features

- Average transaction amount
- Average transaction fee
- Average number of inputs
- Average number of outputs
- Fee ratio
- Input/output ratio

### Wallet Features

- Total number of transactions
- Total amount sent
- Total amount received
- Number of incoming transactions
- Number of outgoing transactions
- Largest transaction
- Smallest transaction
- Number of unique counterparties
- Wallet age

### Time Features

- Transactions per hour
- Transactions per day
- Transaction velocity
- Average time between transactions
- Number of very fast transactions
- Number of transactions occurring within a burst period

### Graph Features

- Degree
- In-degree
- Out-degree
- PageRank
- Betweenness centrality
- Clustering coefficient
- K-core value
- Number of nearby peer wallets

### Network Features

- Number of unique IP addresses
- Number of unique ASNs
- Number of unique countries
- IP change frequency
- Destination port diversity
- Country network diversity

Ground-truth columns such as `is_suspicious` and `pattern_type` are not used as ML input features. This prevents data leakage.

## 8. Isolation Forest in Simple Words

Isolation Forest detects unusual wallets.

It creates many random trees. A wallet that behaves very differently from other wallets is isolated using fewer splits. Therefore, it receives a lower anomaly score.

Important interpretation:

- More negative score = more anomalous
- Higher score = more normal

The algorithm is useful because real investigation data usually does not have complete labels for every suspicious wallet.

---

## 9. HDBSCAN in Simple Words

HDBSCAN groups wallets that behave similarly.

It can also identify wallets that do not belong to any strong group. These wallets receive cluster label `-1` and are called noise or outliers.

The system scales the features first because transaction counts, times, and graph values have very different numerical ranges.

The anomaly score is kept separate from clustering so that HDBSCAN discovers natural behavior groups instead of simply grouping wallets by an already-generated anomaly score.

---

## 10. Risk Scoring

The system uses two sources of evidence:

1. Isolation Forest anomaly score
2. HDBSCAN outlier status

The anomaly score contributes up to 80 points. Being an HDBSCAN outlier adds up to 20 points.

The final score is clipped between 0 and 100.

Risk flags are:

- HIGH: both anomaly and cluster outlier
- MEDIUM: only one of the two conditions
- LOW: neither condition

These alerts are decision-support signals. They are not proof of criminal activity.

---

## 11. Explainability

The explainability module uses a z-score.

The z-score tells us how far a wallet's feature is from the normal average.

```text
z-score = (wallet value - average value) / standard deviation
```

A large positive value means the feature is unusually high. A large negative value means the feature is unusually low.

The system selects the three most unusual features and writes a simple explanation for the investigator.

## 15. Common Questions and Easy Answers

### What is the purpose of the project?

The purpose is to find unusual Bitcoin wallet behavior and help investigators prioritize wallets for further analysis.

### Why is the system offline?

The system must work without Internet access. This improves privacy and allows it to run in restricted environments.

### Why did you use synthetic data?

Real investigative blockchain data may have privacy and security restrictions. Synthetic data allows testing with known normal and suspicious patterns.

### How many records did you use?

The main pipeline uses 493 transaction records and creates 141 wallet profiles. The separate Random Forest dataset contains 20,000 transaction records, with 16,000 used for training and 4,000 for testing.

### Which model is used in the main pipeline?

The main pipeline uses Isolation Forest for anomaly detection and HDBSCAN for clustering.

### Why use Isolation Forest?

It is useful for finding unusual data points without needing labels for every record.

### Why use HDBSCAN?

It groups similar wallet behaviors and identifies wallets that do not fit into normal groups.

### What does `-1` mean in clustering?

It means HDBSCAN considers the wallet a noise point or outlier.

### What does a negative anomaly score mean?

In this implementation, a lower or more negative score means the wallet is more anomalous.

### What is a HIGH alert?

A HIGH alert means the wallet is both anomalous according to Isolation Forest and an outlier according to HDBSCAN.

### What is the difference between a risk flag and a risk score?

The risk flag is a category such as HIGH, MEDIUM, or LOW. The risk score is a numerical value from 0 to 100 used to rank wallets.

### Why should ground-truth labels not be used as features?

Using them would give the model the answer in advance. This is called data leakage and would make the evaluation unreliable.

### What does explainability do?

It identifies the top three features that differ most from the average wallet and writes them in human-readable form.

### Does a HIGH alert prove criminal activity?

No. It only indicates unusual behavior. An investigator must review the evidence before making a conclusion.

### Does an IP address prove wallet ownership?

No. IP addresses can be shared, dynamic, proxied, or used by multiple people. The system treats IP-wallet links as investigative associations only.

### What is precision?

Precision tells us how many flagged wallets were actually suspicious.

### What is recall?

Recall tells us how many of all actual suspicious wallets were detected.

### What is F1 score?

F1 score balances precision and recall into one value.

### Why is the recall only 25%?

The current system is a development version. The feature set, thresholds, synthetic patterns, and unsupervised models do not detect every suspicious wallet. This is a limitation that can be improved later.

### Can this be used directly in production?

Not yet. It requires testing on real validated data, threshold tuning, better entity resolution, time-based evaluation, and additional monitoring before production use.

### What improvements can be made?

Future improvements include larger datasets, more realistic suspicious patterns, better thresholds, SHAP explanations, real-time processing, analyst feedback, and improved graph analysis.
